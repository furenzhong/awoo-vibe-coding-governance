# 最小执行与交接合同

合同修订：v1.6.0 候选，任务和回执字段保持兼容。适用于单个 AI 持续开发，以及一个 AI 调用另一个执行器。本文定义需要保存的事实，不实现编排框架，也不绑定模型名称。

## 什么时候需要它

仅使用当前会话完成小改动时，不必额外建立任务 JSON。出现跨会话长任务、外部执行器、并行写入或需要恢复的操作时，复用项目已有任务记录，补齐以下合同。项目已有可用系统时优先映射或导出所需字段，不再建立同义任务表。

文档告诉执行者目标与边界；CLI、权限配置和隔离环境负责实际执行限制。写了“禁止”不代表系统已经阻止，独立 Git worktree 也不隔离数据库、端口、进程或 API 账户。

项目采用[会话事件记录](CONTEXT_CAPTURE.md)后，派工/接回先核对相关绑定的待处理输入与来源变化；给接收者可访问的必要背景，不能只交原机器的私有路径。没有原生 hook 的工具继续按任务检查点和模型协助记录运行，报告不可见尾部。记录事件不会自动纠偏正在运行的执行者，未知运行状态仍应先定位原操作。

## 一个任务，一份生命周期

根目录 `project-os.json` 的 `tasks_dir` 指向任务记录，`evidence_dir` 指向证据目录；默认分别是 `project-os/tasks/`、`project-os/evidence/`。任务 JSON 是该任务生命周期的唯一来源。项目 STATUS 只保留项目级结论和任务链接，HANDOFF 只链接任务并记录交接现场，不再次填写任务状态。

| 必填字段 | 含义 |
|---|---|
| `id` | 在项目内稳定且唯一的任务标识 |
| `objective` | 需要改变的行为或结果；不把内部实现步骤当目标 |
| `base_revision` | 开工代码基线；Git 项目使用完整提交 SHA |
| `writable_paths` | 允许写入的项目相对路径数组；共享资源边界另在相关合同中说明 |
| `acceptance_commands` | 相称检查的命令数组；命令本身不代表已经执行 |
| `status` | `planned`、`running`、`submitted`、`accepted`、`returned` 或 `blocked` |

委派时再填写 `executor`、`worktree`、`session_id`，分别指明执行者、实际开发目录和可明确恢复的会话。运行中的委派不得靠“最近一次会话”猜测对象。`receipt` 为项目根目录相对的回执 JSON 路径。运行专属绝对路径或会话标识只在子项目保存，不写回公开母版。

验收命令不能表达的条件，例如用户能否完成关键流程、文案是否符合真实资料，仍写在任务对应的业务合同或验收文档中并由任务链接它。没有 Git 的项目可以采用同样的文档合同，记录文件 hash 与实际基线；v1.1 的机器任务／回执检查仅支持本地可解析的 Git 提交基线，尚不支持非 Git 任务 JSON。不要填假 SHA 或声称已完成自动核验。

## 派工、写入和接回

1. 负责人读当前规则、STATUS、相关合同，确认已有授权覆盖目标。已授权的普通实现、相称检查及返修由 AI 推进，不逐项请用户批准。
2. 核对真实基线、工作目录、未提交改动和任务边界，登记任务后再调用执行器。需要隔离写入时建立独立目录；同时明确测试数据、进程、端口及外部调用归属。
3. 每个可写范围只有一个当前写入方。修改相同文件或依赖前一任务结果的任务顺序执行；并行仅用于可独立推进的范围。
4. 执行者只交范围内的改动和回执，终止自己创建且仍会写入的临时进程，停止向交付分支追加改动。此时状态为 `submitted`，不是 `accepted`。
5. 集成者核对实际 diff、基线、最终提交、检查覆盖和未覆盖项，再按改动独立复核。通过后记录验收证据并更新为 `accepted`；有具体问题记 `returned`，给出返修范围。实际条件阻塞才记 `blocked`，可独立推进的工作继续。

跨会话或委派需要保留“为什么这样做”与具体执行现场时，使用 [任务上下文与恢复合同](TASK_CONTEXT.md)：固定派工版本，各执行身份分别保存检查点，纠偏区分记录、送达和采用，接回核对实际采用版本。它扩充现有任务，不增加第五个全局事实来源。重大理解分歧用早期关键选择或小样验证；普通机械修改直接推进。

当执行依赖服务器、后台或本地工具时，必要背景还包括正确环境、入口、身份与凭据获取位置、已验证可行的步骤，以及当前操作的停点和查询定位。稳定知识复用已有操作说明，临时现场写检查点；以“缺少后是否会重问、重试、错环境或重复操作”判断必要性，不复制全部聊天和工具输出。不得将凭据值、仍有效的登录态或当前进程状态作为无需核实的默认背景。

用户主动要求换会话前更新治理时，按上述合同检查遗漏、更新原职责文件并给出入口。分别说明已保存、已核对与实际接续是否验证；不新增每会话任务表、自动触发或清理。调用另一个执行器时，除了保证材料可读，还应确认它能访问必要的操作环境；指向负责人机器的私有路径不能证明对方可用。

不规定 Codex 必须指挥 Claude Code，或反过来。负责人可以兼任执行者；发生委派时，集成验收不能仅复述执行者的“成功”回执。

## 回执是交付事实，不是第二份状态表

回执 JSON 的字段如下；所有证据路径相对项目根目录，不含凭据或私有响应正文。

| 字段 | 含义 |
|---|---|
| `task_id`、`base_revision` | 必须匹配任务 |
| `result_revision` | 实际交付提交，Git 项目必须能核查对象与基线关系 |
| `changed_files` | 实际改动文件数组；集成者对照 diff |
| `checks` | 实际执行的检查数组，每项含 `command`、`exit_code`、`evidence`，其中 `evidence` 是单个证据文件路径 |
| `evidence` | 其他交付证据文件路径数组；没有就保留空数组，不造记录 |
| `verified_by` | 验收者；进入 `accepted` 前必填 |
| `verification_evidence` | 独立验收证据文件路径数组；进入 `accepted` 前至少一项 |

回执不保存任务 `status`。提交者提供交付事实，验收者补验收部分；如发现事实不符，保留原证据并追加纠正，不把失败原件改成成功。离线检查、真实服务运行、外部 API 成功和人工质量验收分别说明覆盖范围。进程退出码 0、JSON 合法或模型说“完成”均不等于业务验收通过。

## 中断后先查现场

控制会话超时、工具断线或上下文压缩，不表示任务已经停止。

1. 从任务取明确的执行目录、基线和会话标识，读当前上下文版本、相关身份的检查点、待采用纠偏、已有回执与证据。负责人自己的压缩或换会话同样执行此步。
2. 核对正确环境、当前身份与必要访问方式，再检查执行器是否仍运行、实际 Git 状态、交付文件是否已形成、是否仍有写入进程。已有运行继续观察；已有交付先验收。访问曾成功只是带时点的观察，不等于登录态可以跨会话继承。
3. 确认需要续跑时，恢复指定会话或从已有检查点继续，不能直接复制同一任务重新派发。
4. 已发生外部写入或付费调用时，先依据原操作 ID／回执查询结果。无法确定是否受理时保留未知，不因等待超时自动重发。
5. 只有基线、写入归属或授权实际冲突、且现有证据无法解决时，向用户说明具体缺口。恢复事实回到同一任务记录。

## 工具适配与检查边界

适配器只需能明确传入目录、任务上下文与执行限制，保存会话、输出和退出情况，并恢复指定会话。配置应记录实际加载的规则文件。不同工具的项目入口可链接 canonical AGENTS；需要 import 的工具应使用其支持的 import 语法，不能假定一条普通链接等于自动加载。

不默认放宽工具权限，不把工具特有的模型、参数和认证方式写死进通用治理。采用某个 CLI 时核对其当前官方文档，再增加局部适配说明。

运行 `python scripts/project_os.py check --target PATH` 可检查映射、任务与回执结构、引用文件及部分 Git 关系。启用可选 `context` 后，还检查派工 hash、版本与身份引用、纠偏证据及过期验收。旧任务兼容，但报告不声称覆盖新协议。它不执行 `acceptance_commands`，不确认日志真实、审核者身份、业务效果或文档语义正确。`accepted` 的结构检查通过，也仍需要实际验收。

部署入口见[部署指南](../03_DELIVERY/DELIVERY_PROJECT_INSTANTIATION_GUIDE_v1.md)，如何验证治理真的有用见[治理试用](../03_DELIVERY/GOVERNANCE_TRIAL.md)。
