# AI 生成代码审查协议

协议版本：v1.7.0 候选（在 v1.6.0 候选的 6 步流程上增量修订）

本协议将风险分类转为可复核的审查过程，重点发现代码、配置、数据、权限和运行行为组合后的缺陷。它补充 `AGENTS.md` 中的组合行为验证要求，不以长清单打勾代替验证，也不把流程存在当成缺陷检出率保证。

## 审查范围

审查前确认产品、代码版本、部署环境、变更范围、只读/修复授权，以及不可访问的数据或外部系统。先读取当前项目规则、状态、决定、任务合同、相关实现和配置。对“已脱敏”“已修复”“已上线”等继承来的输入假设抽样核验；未经核验不得当作事实。

本协议自带最小风险分类法；它是审查方向的权威起点，不是逐项打勾清单：权限与身份、状态与一致性、幂等与重复、失败与恢复、文件与路径、凭据与秘密、依赖可达性、供应链与构建、网络与外部副作用、输入与边界、覆盖与可观测性。每个项目仍须按实际架构裁剪，并在适用性矩阵中保留裁剪理由。若项目采用其他分类法，必须声明分类法来源、替代关系和覆盖差异。对每个分类标记 `applicable`、`not_applicable` 或 `unknown`；证据不足不得判为通过。

## 审查步骤

### 1. 划定产品边界

识别身份、权限、租户和数据访问边界；支付、发信、删除、发布等外部副作用；关键状态转换；失败、重试、并发、超时、断线和进程重启行为；敏感数据进入日志、缓存、模型提示、错误消息和备份的路径。

记录权威来源裁定：项目已有 `AGENTS.md`、合同、状态、决定和运行说明时说明采用哪一份；没有项目级 `AGENTS.md` 时，审查者必须写明替代文档及理由，并说明选错会影响哪些结论。

### 2. 写出不变量与反例

每个高风险检查先写必须始终成立的业务不变量，再设计至少一个可能使实现失败的反例。优先挑战模块之间的连接点，例如 controller→service、service→repository、数据库→缓存、主流程→队列、应用→第三方 API。

| 风险 | 不变量 | 反例 |
|---|---|---|
| 租户隔离 | 查询、缓存和异步任务都不能跨租户返回数据 | 先请求租户 A，再请求租户 B，比较缓存响应归属 |
| 幂等支付 | 同一业务操作最多产生一次扣款 | 第三方扣款成功后让本地请求超时，再用同一 key 重试 |
| 权限撤销 | 撤销后旧 session 不能继续执行受保护操作 | 撤销权限后重放旧 cookie、token 或后台任务 |
| 稳定分页 | 稳定排序下翻页不会静默漏行或重复 | 翻页期间插入/删除记录，再核对跨页结果 |
| 正确接续 | 新执行者不把未核对摘要当作当前事实 | 给出过期摘要，观察是否先核验现行权威来源 |

### 3. 静态检查

检查实现、配置、依赖、迁移、权限声明、错误处理、日志、测试和部署边界。静态存在某段代码只能支持有限推断，不能证明运行行为可靠。每条发现定位文件、符号、配置键、请求路径或数据流，并说明它与不变量的关系。

### 4. 执行反例

对 P0/P1 风险，必须执行适用的最小复现、测试、接口/浏览器操作、数据库验证或受控故障注入。每个高风险检查至少记录一条场景：前置状态、操作序列、预期结果、实际结果、判定依据和证据 ID。按风险覆盖失败和边界输入、旧数据、重复/重试、并发/超时、越权/凭据撤销，以及外部调用成功而本地回执丢失等部分成功状态。

记录目标版本、环境、实际命令或操作、退出码和原始输出位置。适用的 P0/P1 验证未能执行时，只能记录 `unknown` 或 `partial`、说明阻塞与残余风险，不能标记 `pass`。只有明确的风险责任人接受残余风险，才能另行记录风险接受；它不改变验证结果。测试夹具写出“成功”或静态检查通过不能替代行为证据。

对每个适用的 P1 单独声明“已执行、未执行或降级”、理由、替代证据和残余风险接受人；未声明不得以降级规避执行。目标项目只读时，证据写入 `<audit>/work/<project>/evidence`，并在记录中声明回退位置及目标项目不可写的依据。

### 5. 独立复核

独立性由材料、检查问题、执行过程和结论是否与初审实质隔离决定，不由模型名称变化或更换对话自动产生。复核者读取代码、配置和验证证据，尝试推翻至少一个高风险结论；优先在未看到初审结论时形成自己的检查问题。检查推断是否冒充事实、是否存在未执行却宣称验证、是否漏掉组合路径、适用性判断错误、测试环境掩盖风险，以及未知范围遗漏。

记录复核者、时间、是否隔离初审结论、复核者与初审者是否同一模型/同一委托链、被挑战的检查编号、挑战操作、预期/实际结果及证据引用。复核不能只重复初审摘要。

### 6. 记录和报告

每个项目审查使用 [记录模板](templates/AI_CODE_REVIEW_RECORD_TEMPLATE.md)，按风险项重复检查记录。分别记录适用性、不变量、反例、检查动作、证据、结果、严重程度、未覆盖范围、残余风险、修复建议和修复后复验条件。

严重程度：

- `P0`：可能造成大规模数据泄露、资金损失、不可逆破坏、生产完全不可用或绕过关键安全边界。
- `P1`：影响重要客户、关键业务流程、权限边界、数据完整性或恢复能力。
- `P2`：局部功能、性能、可维护性或中等运营风险。
- `P3`：低影响问题、文档缺口或改进建议。

校准锚点（单机/单用户也适用）：本地 API 未鉴权且可把凭据发往外部地址，或路径穿越可删除用户数据，通常至少 `P1`；若可在默认暴露面无交互地造成跨账户/跨家庭泄露、关键凭据外发或不可逆破坏，可为 `P0`。仅局部错误、需要额外前置条件且不影响权限/完整性的通常为 `P2`。P0/P1 边界有争议时必须写一句依据、触发条件和影响范围，不能为逃避执行要求下调严重度。

先报告 P0/P1，再报告 P2/P3。摘要可以聚焦最值得处理的十项，但完整记录必须保留，且未知项不能被摘要省略成“均通过”。

## 证据与结论

证据按实际内容标记，可并存：

- `observed`：实际查看了代码、配置或文件；
- `inferred`：静态推理，未执行；
- `executed`：命令、测试或操作实际执行并保留结果；
- `adversarial`：边界、越权、重复、并发、故障或攻击反例实际执行；
- `independently_reviewed`：独立审查者核对证据并挑战结论。

依赖可达性、凭据/秘密和覆盖范围必须单独记录；依赖声明存在或静态命中不能推出运行时可达，明文秘密未进入构建产物也不能推出已处置。对完整交付，除失败发现外还必须记录已验证安全的负结果；没有写“未发现”不等于做过检查。跨项目出现同一组合模式时，另行汇总模式、受影响项目、共同触发条件和是否需要修订协议。

每条结论可关联多条证据。`pass` 仅覆盖列明的场景和版本；不代表整个产品安全、可靠或已经业务验收。记录已保存不表示问题已修复、用户已接受或其他执行者已采用。

## 与治理来源的关系

本协议定义可复用审查步骤；项目 `AGENTS.md` 只引用并说明稳定约束；每次审查记录与原始证据保存在目标项目的 evidence 目录，目标只读时按第 4 步回退；用户确认、否决或风险接受按项目决定文件维护；进行中的审查任务和停点按任务/交接来源维护。不要在多个索引复制同一审查结论。
