# 任务上下文与恢复合同

合同修订：v1.6.0 候选；可选 JSON 扩展仍为 `context.schema_version = 1`，不迁移旧任务。基础任务和回执见 [Harness 合同](HARNESS_CONTRACT.md)。

目标是让接手者找回**会改变下一步选择的依据和现场**。例如，Codex 知道用户只允许主动清理文档，Claude 只收到“补充交接机制”，便可能加入“交接时自动归档旧计划”。计划再详细，如果少了这条约束及原因，执行仍可能偏离。

这里保存可共享的结论、证据和未决事项，不要求导出内部思考、聊天全量记录或每次自动压缩摘要。即使拿到了工具原生摘要，也只将其当恢复线索；不能假定所有工具暴露相同摘要或压缩前 hook，不能承诺任意多次切换无损。

v1.5 的[可选事件记录](CONTEXT_CAPTURE.md)为本合同提供来源证据和缺口报告。恢复时核对有关绑定的待处理输入、最近原话、当前来源及真实操作，再决定下一步；`no_change` 和完整水位不能替代这一步。捕获 ID、检查点版本和派工版本独立，压缩本身不增加新要求。纯讨论留在专题和讨论绑定，不补造执行任务。录入、语义核对、文件已写、消息已送达及执行者已采用仍分别留证。

## 归属与启动

`rules/status/handoff/decisions` 四个全局来源不变。用户确认的长期约束和决定仍在原来源；任务 JSON 是唯一任务生命周期。只在已有工作确实需要跨会话、委派或恢复时使用本合同；单会话小改动无需全套记录。已有平台能承担这些职责就复用，需要本地机器检查时导出相应结构。

在派工、实质选择确定、用户重要纠偏、形成有用现场或准备交接时维护任务记录。有变化才写，不每轮总结，不建定时提醒，不等“马上压缩”才保存。它属于当前已授权工作的事实维护。**文档盘点、合并压缩、归档和删除仍只在用户明确请求时启动**；换会话、压缩、交接或纠偏都不构成清理请求，也不因此询问是否清理。

| 记录 | 维护者与用途 |
|---|---|
| 当前要求与决定 | 项目负责人维护既有权威来源；注明来源、适用范围和替代关系 |
| 任务 JSON | 任务负责人维护状态、当前执行身份及当前上下文版本 |
| 派工快照 | 负责人固定当次交付内容；保留历史版本，不就地改写 |
| 恢复检查点 | 每个活跃身份各维护一份，包括负责人；记录最后观察与下一步 |
| 纠偏及送达证据 | 负责人记改变、对象与送达事实；执行者提供采用及影响证据 |
| 项目 HANDOFF | 只导航到任务及检查点，不让多个 AI 轮流覆盖同一份总记忆 |

一个可写范围同一时刻只有一个执行写入方。需要并行就拆任务；转交身份时先核对旧写入者是否停止。文档登记不提供操作系统层面的互斥。

## 用户准备换会话时

用户明确说“准备换新对话，更新一下文档治理”时，在本次授权范围内完成交接。这个入口不新增定时保存、每轮总结、退出拦截或清理提醒；原有任务事实维护照常进行。先查看本轮仍可访问的输入、实际产物和既有来源，不把当前摘要当作完整聊天，也不声称找回已经不可见的细节。

1. 找出尚未落盘、会改变接手者下一步的决定、纠偏、否决原因、观察结果及未决问题。与现有来源核对后只更新有变化的对应文档；旧要求已经被替代时说明替代范围。
2. 检查必要操作知识和未完成现场，按下节归属保存。已有任务就更新该任务及相关身份的检查点；没有独立任务需求时复用现有工作记录和交接，不为换会话强制新建任务 JSON。
3. 在 HANDOFF 链接当前状态、相关任务、操作说明和检查点。避免把同一内容再完整抄一遍；不为每次会话另建一套“当前状态”。
4. 从这些入口核对接手所需内容是否可找到、互相一致、仍有证据支持；能读取文件不等于已验证当前连接、登录态或运行状态。实际操作验证只在已有授权和适当环境内进行，未做就写未测。
5. 给用户简短交接回执：新会话入口；已保存的变化；核对范围与缺口；实际接续验证结果或未测。只有无法从现有材料查明、且影响继续执行的信息才提问，问题指向具体缺口，只暂停依赖动作。

这份回执是交接结果的简述，不是新增必填 JSON 或另一份状态来源。**内容已写入、接手所需内容已核对、实际接续已验证是三件事**。不能因文件齐全或记录水位完整就把三项都报为通过。

## 操作知识与临时现场

判断保存必要性的标准是：**缺少它，下一位 AI 是否会再次问用户、重复试错、操作错环境，或重复执行已经受理的动作？** 只保存与后续行动有关且可查证的信息。无需逐条转存工具日志，也不要求没有服务器的项目填写服务器表。

| 内容 | 归属与按需保留的细节 |
|---|---|
| 相对稳定的访问和操作知识 | 优先更新已有部署／操作说明（runbook）：目标环境及用途、实际入口或主机别名、已成功的连接方式、账号身份／角色、凭据获取位置、必要步骤及成功判断；记录最近验证时间、条件和证据 |
| 本次未完成的操作 | 既有任务／身份检查点：已执行动作与观察时间、进程／会话／外部操作 ID 和查询方式、上次结果、剩余动作、重复执行的影响及未知项 |
| 项目交接入口 | 链接上述来源和具体停点；需要继续前核实的事项明确列出，不复制整份操作手册 |

操作说明只存凭据定位和获取方式，不存密码、令牌或带凭据的 URL／命令。接手者未获访问权限时如实说明；以前连接成功不能证明当前身份、凭据、后台登录态或服务器环境仍相同。查询应先确认环境与身份；若已有操作 ID，先查原操作，不因超时或旧记录标为 running 就重发。

若已有操作说明只缺一条成功步骤，补该说明即可。确无可复用来源而任务又确需长期操作知识时，才按项目已有目录约定建立一份说明；不新增全局事实来源。检查点继续使用现有字段：`last_action` 写实际动作与结果，`observed_at` 写观察时点，`operations[].locator` 写可用查询定位，`unresolved` 写缺口，`next_action` 写下一步，`evidence` 链接记录。状态未知就保持 `unknown`，不用新字段掩盖未知。

公开形状和离线探针见[操作接续示例](../../examples/continuity/README.md)。示例中的身份、环境和操作 ID 都是合成数据，不能作为真实接入证据。

## 派工时固定必要背景

每份快照包含本次目标、用户约束及可访问来源、影响实现的已否决方案与原因、假设和验证时机、非目标、验收依据。来源应具体到决定编号、文件版本或保留下来的授权摘录。不能只给几十个链接；关键约束写明，补充背景按需引用。无法确定来源的断言标为待核实，不当作用户要求。

快照是“当时发出了什么”的证据，不是另一份当前权威。要求改变时先更新对应来源，生成新快照并推进任务版本；旧快照继续保留。不要回改旧快照，制造执行者从一开始就收到新要求的假象。

派工时确认实际工作目录中能读取快照和必要来源。另一个 worktree 不会自动带上负责人的未提交文件；需提交、复制所需材料或把内容作为实际输入交付，并核对版本。回执记录实际采用版本。读过、回复“收到”或通过 hash 检查都不证明理解正确。

若任务有实质方向选择，让执行者尽早展示一个关键选择及其依据，或最小代表性结果。例如展示交接如何只保存检查点、不会自动清理。负责人据现有授权核对后继续；普通替换、格式修改不增加审批仪式。只有现有材料无法裁定的用户意图或权限才提问，说明具体冲突与影响，等待期间保留材料并推进独立工作。

## JSON 结构

路径相对**目标项目根目录**，不得越界；任务附属 JSON 放在任务子目录，避免被顶层任务扫描误认。完整形状见 [示例](../../examples/context/README.md)。

```json
"context": {
  "schema_version": 1,
  "current_revision": "ctx-002",
  "snapshots": [
    {"revision": "ctx-001", "path": "project-os/tasks/export/context-001.md", "sha256": "实际摘要"},
    {"revision": "ctx-002", "path": "project-os/tasks/export/context-002.md", "sha256": "实际摘要"}
  ],
  "checkpoints": [
    "project-os/tasks/export/coordinator.json",
    "project-os/tasks/export/executor.json"
  ],
  "corrections": ["project-os/tasks/export/correction-001.json"]
}
```

`snapshots` 按产生顺序列出，版本唯一，`current_revision` 必须指向最后一项。每个后续版本都要有纠偏记录说明变化；当前要求若恢复旧方案，也创建新版本说明原因。SHA-256 计算规则为：读取 UTF-8 文件的原始字节，仅将 `CRLF` 替换成 `LF`，再计算 SHA-256；不去 BOM、不 trim、不做其他规范化。换行转换不会误报内容变化，其他变化会报错。若同时改内容和登记摘要，工具无法还原旧内容；Git 历史与独立证据仍然必要，hash 不是身份认证。

每个 `checkpoints` 文件的必填字段：

| 字段 | 含义 |
|---|---|
| `task_id`、`actor`、`role`、`session_id` | 任务、身份说明、`coordinator` / `executor`、可定位的实际会话；actor 文本不是身份认证 |
| `context_revision` | 该身份实际采用的快照版本，可以暂时落后，不能为通过检查谎改为最新 |
| `observed_at` | 带时区的观察时间，例如 `2026-09-27T10:00:00+08:00` |
| `last_action`、`next_action` | 最后实际动作及结果、下一步；“准备测试”不能写成“测试通过” |
| `unresolved` | 未解决问题、假设及应验证的条件，字符串数组，可空 |
| `operations` | 操作数组，可空；每项 `description`、`locator`、`state`；state 为 `running/completed/unknown`，仅表示上次观察 |
| `evidence` | 已存在的证据文件路径数组，可空；不得为了完整伪造证据 |

可增加与任务有关的失败尝试、观察和来源，但不复制全项目历史。活跃列表同一 `role/session_id` 只能有一个检查点；旧身份记录留作历史，不混进活跃列表。负责人和执行者记录分别写。检查点不另存任务 `status`。已开始的任务缺负责人检查点会提醒；检查器不能认证哪一个负责人会话当前活跃。

恢复时读取当前规则、任务、自己及有关执行者检查点、实际采用快照、当前版本和未采用纠偏，然后只回查本次行动所需来源。以原始决定和新增证据更新，不不断摘要上一份摘要。如果负责人换了会话，也必须完成这套核对。

## 纠偏不是写一段备注

每份纠偏 JSON 必填：`id/task_id/from_revision/to_revision/cause/reason/impact/target_session_id/delivery/delivery_evidence/adoption_evidence`。两版本必须属于同一任务且向更新的快照推进；`snapshots` 按产生顺序列出。原因枚举：

- `handoff_omission`：负责人漏交已有约束。
- `execution_deviation`：执行者偏离已交付要求。
- `requirement_change`：用户后来改变要求。
- `acceptance_gap`：原验收依据遗漏了重要条件。

`reason` 说明原依据、发现的差异和新决定；`impact` 说明受影响的在途工作、可复用部分及应重验的范围。不要把后来变更的需求全部归咎于执行者。

| `delivery` | 能据实声明什么 | 证据要求 |
|---|---|---|
| `recorded` | 已写下，尚未证明送达指定会话 | 两类证据数组可以为空 |
| `delivered` | 已通过实际通道送到指定会话 | `delivery_evidence` 至少一个文件 |
| `adopted` | 指定会话已说明采用版本、受影响改动和后续处理 | 两类证据都非空；`adoption_evidence` 使用保留的响应/验收记录，不能只指向之后会覆盖的活跃检查点 |

证据文件应保留实际输入/响应中与任务有关的片段、会话标识、版本和影响判断，去掉凭据。检查器只核对结构、存在性和部分一致性，不能认证事件确实发生，更不能认证模型理解。

**一次性调用**中，当前执行可能无法接收消息：保持 `recorded`，独立工作继续，等返回后核对旧成果和受影响范围，再用新输入返修或重验。不要把“文件已更新”写成“已通知”。**可续会话**中，向明确会话发送新版本和差异，保留送达与采用响应，随后更新它自己的检查点。需要暂停写入时由真实执行层完成并核实，Markdown 不能停止进程。

旧会话无法再回应时，不伪造它的采用。保留旧回执和未送达记录，核对它是否已停止，明确转交给新执行身份；新身份依据当前版本检查/修复候选成果，形成自己的检查点与回执。旧成果只在已核实范围内复用。

## 接回与中断恢复

启用 `context` 的任务，回执增加 `context_revision` 和 `checkpoint`。后者须引用活跃 executor 检查点，任务、会话及版本匹配。提交旧版本结果可保留为 `submitted` 并报告提醒；**不能直接标为 `accepted`**。当前执行会话仍有未采用的相关纠偏时同样不得验收。对旧结果先记录具体影响并返修/重验，不默认全盘丢弃，也不只改版本号“补齐”协议。

1. 恢复者先确认自己适用的当前依据和待送达纠偏，不依据旧摘要直接派工或验收。
2. 核对指定目录、实际 Git/未提交改动、已形成的回执以及执行器现场。上次记为 running 不等于现在仍运行；没有查询结果也不等于已停止。
3. 已有运行先定位观察，已有交付先审查。只有核实有必要续跑时才恢复指定会话或转交身份。外部操作先查原操作 ID，结果未知时不自动重发。
4. 检查业务行为、真实 diff、当前约束与相称测试，再记录独立验收。checkpoint 的“已完成”不替代验收证据。

`check` / `snapshot` 的 `context` 报告列出 `tracked`、`legacy` 和 `state`：`not_exercised`、`legacy_only`、`tracked_records_checked`、`partially_covered` 或 `records_invalid`。没有活动任务时不能声称执行过协议；旧任务仍可通过原检查，但明确没有覆盖本扩展。机器检查不运行调用、测试或纠偏投递；它也无法保证声明的材料全部相关、背景完整、日志真实。

升级时从新产生的真实任务采用即可，不补造旧历史。第一次采用应执行 [接力故障挑战](../03_DELIVERY/GOVERNANCE_TRIAL.md)，再观察真实接手是否减少重复劳动和人工纠偏。
