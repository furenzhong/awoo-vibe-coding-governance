# 治理保证架构方向

状态：演进方向，不是当前已实现能力。当前可用能力以 `project_os.py check`、回归测试和各项试验记录为准。

## 目标

让治理要求能映射到可观察证据，让机器暴露结构和证据缺口，让独立挑战检验规则效果，并让人对业务语义、影响和残余风险作最终判断。任何单一规则文件、检查器 PASS 或模型自述都不构成完整保证。

## 分层边界

| 层 | 职责 | 当前状态 |
|---|---|---|
| 项目事实与合同 | 保存目标、约束、权威来源、范围和验收条件 | 由项目现有文档维护 |
| 证据绑定 | 关联代码 revision、环境、命令、结果、原始输出和覆盖 | 记录模板支持；机器只做有限结构校验 |
| 本地结构检查 | 发现必需章节、引用或记录形状缺失 | `project_os.py check` 增加显式标记审查记录的结构检查 |
| 行为挑战 | 在隔离样本中检验缺陷检出、正确实现误报和盲区 | trial v2 已完成合成样本测试和两次独立会话复核；模型/委托链独立性与检出率仍未知 |
| 独立复核 | 从目标和原始证据重建检查问题，挑战高风险结论 | 由审查记录和实际隔离过程证明，模型名称不是证据 |
| 决策与风险接受 | 由有权责任人处理业务歧义和未解决风险 | 保持人工/项目责任边界 |

## 演进顺序

1. 先让本地检查器对显式版本化记录做有限结构校验，并保留旧记录兼容。
2. 为协议变化维护隔离的正例、负例和无权威入口样本；记录误报、漏报、未测范围和版本。
3. 只有多轮样本证明手工维护成本或检查覆盖存在稳定瓶颈后，再抽象可配置的规则包、验证器接口和统一证据格式。
4. MCP、API 或桌面软件可作为后续适配层；它们负责接收输入、运行适用检查和返回证据引用，不能代替授权、业务判断或独立验收。

## 当前边界

当前检查器不运行产品测试、不扫描所有仓库安全问题、不判断字段内容是否真实，也不会证明 AI 采用了规则。审查记录只有声明 `record_type: ai_code_review` 才参加审查结构检查。读写权限、外部系统、生产数据和真实秘密仍由项目授权及安全流程控制。

是否进入通用规则引擎或服务化阶段，应由重复出现的真实审查案例、已记录的漏检/误报和可复现的维护成本推动；如果后续样本显示结构检查造成误报，或维护负担高于减少的漏项，应缩小或撤回该检查。
