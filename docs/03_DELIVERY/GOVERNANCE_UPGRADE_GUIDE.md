# 升级已有项目的治理

适用请求：“依据这个仓库，升级我当前项目的文档治理，保留已经积累的要求和开发现场。”用户给出链接后，AI 负责调查、形成候选变更、验证和落实；用户不需要填写迁移表，也不需要逐文件批准已授权的普通适配。

升级成功的依据是项目能正确接续开发：不会重开已否决方向，不会把已有实现当成待开发，也不会丢掉待定事项或把正在执行的任务重新派发。文件保留和机器检查是必要证据，不足以单独证明成功。

本指南落实[升级方案](GOVERNANCE_UPGRADE_PLAN.md)。工具的实际验证范围以[当前状态](../00_PROJECT_CONTROL/PROJECT_CURRENT_STATUS.md)为准。不要把本地实现解释为已经发布的版本，或把某个样本通过解释为所有项目均已兼容。

## 1. 先识别现场，不按文件名猜版本

保持源工具包与目标项目分开，核对目标路径、Git 身份、未提交改动和范围内的活跃写入者。只读取本次适配需要的入口、合同和相关证据；升级不启动全库盘点、归档、压缩或删除，也不主动询问是否清理。

把现有材料对应到以下职责。路径与名称可以不同，不要求搬迁历史。

| 职责 | 目标已有材料的处理 |
|---|---|
| `rules` 稳定规则 | 复用现有共享规则；合并新机制时保留项目约束 |
| `status` 当前事实 | 指向现有事实入口；专题事实继续在专题维护，入口引用 |
| `handoff` 未完成现场 | 复用当前交接及任务索引，不建立第二套进度 |
| `decisions` 重要决定 | 可以是原有决策索引，由它导航目录式决定记录 |
| 专题合同、执行记录和历史证据 | 原位保留；四项来源按职责引用，不全部改写为新模板 |

若目标从未使用安装器，或找不到可核实的旧采用内容，应明确记为未知。目录叫 `project-os/` 不证明采用过某一版本。没有 manifest 的成熟自定义体系可以按[接入指南](DELIVERY_PROJECT_INSTANTIATION_GUIDE_v1.md)映射职责、补齐必要入口和工具，再对需改动的既有文件做下文的明确升级。先比较 `plan`；不能为了安装工具覆盖既有同名脚本。

`project-os.json` 的 `sources` 仍只有 `rules/status/handoff/decisions`。`.project-os-adoption.json`、升级计划和应用日志保存采用证据，不拥有业务事实，不新增全局 `MEMORY.md`。

## 2. 先检验适配是否保留了理解

在隔离副本做最小适配，核对与任务有关的未提交事实也进入了样本。Git worktree 不自动包含未提交材料。副本排除凭据和生产数据，不运行真实后端、供应商调用或原任务执行器。

先封存答案，再让没有原聊天历史的 AI 从正常入口接手；不能把答案或本轮分析交给它。具体项目应选能暴露方向偏差的案例，例如：

- 旧讨论包含导入恢复，当前仅要求供查看的分类导出；新 AI 应保留“不做导入、具体形式待定”。
- 已有脚本与未来完整交付路线并存；新 AI 应区分已实现、方向确认、尚未实施和未经质量验收。
- 事实入口说功能未实施，但专题和代码已有实现；新 AI 应查证冲突，避免重复开发。
- 用户只要求记录一个新方向；新 AI 应维护专题与必要依据，由入口引用，不向多个入口广播同一份状态，也不启动清理。
- 某执行者尚未收到纠偏；新 AI 应保留原会话与现场，标记待送达，不补造采用、不重复派发、不直接验收受影响结果。

先修正导致失败的最小适配，再复测受影响案例。正常事实修正与治理规则适配属于本次升级；无关历史的清理仍需用户主动提出。实务接手通过后，才把候选变更交给工具落实；机器检查不能代替这一判断。

## 3. 候选内容由 AI 根据证据形成

升级工具接受明确的文件候选，不从版本号推断整个项目该被替换成什么。AI 对每个受影响文件说明职责、来源、当前定制及为什么要改；项目业务要求不能用上游模板覆盖。

| 可核实材料 | 比较与候选要求 |
|---|---|
| 有原实际采用内容 | 比较 base、目标当前内容和 upstream；保留本地定制与新版必要变化 |
| 本地和 upstream 相对 base 都有变化 | AI 提供已经合并的 candidate，并说明冲突如何处理；工具不执行语义合并 |
| 没有可靠旧基线 | 使用 `current_only`；依据当前文件、明确来源和相关证据形成候选，不伪造三方比较 |
| 无法裁定的业务意图冲突 | 保留原文，只暂停依赖该答案的改动，向用户说明具体来源、推荐和影响 |

原采用基线必须能还原实际内容；一个旧版本号、hash 或“看起来像某个模板”不够。新版资源也应绑定真实来源 revision。语义等价、来源真实性和候选是否满足项目意图，仍需 AI 查证；工具读取内容和摘要不证明这些判断正确。

只改后续维护方式时，把“每次方向更新同步所有入口”改为“更新唯一专题、必要决策和引用”。待办只保留状态、下一动作与专题指针，不再复写该专题的业务约束。不要靠在多个文件顶部继续追加“以下是历史”来掩盖互相矛盾的现状。每处改动都应有独立职责。

一份阶段文档可能同时包含已经结束的派工授权和仍有效的稳定约束。结束旧任务时，只结束该任务的授权、状态和时序；核对并保留单方写入、交付停写、数据隔离与接回验收等仍适用的规则，从当前入口引用原条款。不能把整份文件标为历史后让这些规则一并失效。具体执行句已被替代时，在该句旁注明替代来源、适用版本及旧任务例外，保留同段其他有效限制；不让局部检索只能读到失效的强制句。

## 4. 规划、应用与局部回退

由 AI 准备 proposal 和候选文件，再使用源工具包中的升级命令。以下命令从目标根目录运行；示例中的 `../governance-upgrade-work/` 是目标外的独立工作目录，由 AI 创建。精确字段及可运行合成材料见[升级示例](../../examples/upgrade/README.md)。

```text
python ../awoo-governance-kit/scripts/project_os.py upgrade-plan --target . --proposal ../governance-upgrade-work/proposal.json --out ../governance-upgrade-work/plan.json
python ../awoo-governance-kit/scripts/project_os.py upgrade-apply --target . --plan ../governance-upgrade-work/plan.json --journal ../governance-upgrade-work/journal.json
python ../awoo-governance-kit/scripts/project_os.py upgrade-rollback --target . --journal ../governance-upgrade-work/journal.json
```

1. **规划。** `upgrade-plan` 读取当前文件和明确的候选材料，生成目标外的自含计划。计划保留本次比较与应用所需内容；不需要在应用时重新获取上游，也不写目标。AI 检查真实差异和语义依据。
2. **协调。** 重新核对从试点到实际项目期间的新变化，协调将改动文件的实际写入者。无关任务继续执行；未提交工作无需先清空。工具的写前检查不等于锁住所有编辑器、Agent 或进程。
3. **应用。** `upgrade-apply` 先复核计划涉及的全部文件，再在每项写入前复核。先把写入意图持久记录，再写文件和记录实际结果。日志在目标之外，保留前后内容和每项结果，不能只保存 hash 或“升级成功”。
4. **验收。** 核对应用日志与文件现场，运行相关结构检查和已选定的独立接手案例。只登记实际完成的采用范围、来源、定制和验证；未完成或未覆盖的能力如实保留，不只修改 `kit_version` 宣布整体完成。
5. **必要时回退。** `upgrade-rollback` 只对日志中本次变更且现场仍可确认的内容恢复。发生后续修改时自动回退应停止该项，由 AI 比较当前内容并生成局部逆向补丁，保护升级之后的新工作。

应用不是跨文件事务。中途失败时，不能假定全都成功或全都没有发生：读持久日志并重新核对受影响文件，再决定局部恢复或重新规划。崩溃后日志中的写入意图也不等于该文件已写入；应对照日志的前后内容判断现场。不要自动 stash、reset、整库回滚或强制切换业务分支。

新文件以已写完整的临时文件创建，防止覆盖同时出现的文件。若进程恰在创建链接与清除临时名之间被强制结束，可能留下 `.project-os-write-*` 和多重硬链接；工具会保留现场并拒绝该项。先核对日志、文件内容、链接关系及旧写入者状态，再处理确定属于本次操作的临时名，重新执行局部恢复。不能把所有崩溃情形都宣称为自动回退成功；断电后的存储持久性也未专门验证。

应用和回退期间，工具在目标根目录创建临时 `.project-os-upgrade.lock`，用于避免本工具的升级操作互相重叠。它不阻止编辑器或其他 Agent 写文件。若异常退出留下锁，先核对其中的进程信息、相关日志和实际写入者，确认原操作已停止后才由 AI 或用户移除残留锁；不能因为锁较旧、会话看不见或文档说已完成就推定可以重试。

规划后文件有新变化，应重建相关候选和计划；不能通过强制覆盖消除冲突。计划和日志可能包含目标文件正文，应按目标项目的资料权限保存，不能作为公开工具包示例提交。

## 5. 采用记录是证据，不是版本号通行证

新版安装器首次 `apply` 时生成 `.project-os-adoption.json`，记录该次实际采用内容及来源。已有项目重跑 `apply` 不会升级规则或脚本，也不会追补一个无法证明的旧安装历史。旧项目从本次可核实现场开始留证即可。

升级记录需要能回答：哪个职责或组件、哪个路径、来自哪个 revision、实际采用了什么内容、保留了哪些定制，以及经过哪些检查。hash 用来核对字节，内容或可重建补丁才用于比较与恢复。采用记录、计划和日志需要在后续升级时可取得；它们不能取代业务合同或当前状态。

这些证据保留完整字节，体积可能较大。仅在比较、审查采用情况或回退时按需读取，不加入每轮 AI 默认上下文，不把正文复制进当前状态。记录可定位的存放位置，保留下一次比较所需材料；不能因为本次升级结束就把计划、日志和唯一可重建基线全部删除。

目标外的日志不会随目标 Git 仓库自动保存。把所需计划、日志、来源材料和工具版本纳入目标的私有备份安排，记录相对定位和摘要；换目录或换机器后先核对副本与目标身份，不能为绕过工具的身份检查直接改写日志。连续多次升级应保留各次记录并注明先后关系；通常先撤销最近一次，再检查较早升级是否仍可回退。后续工作与升级交错时形成局部逆向补丁，不用较早日志覆盖后来成果。公开发布工具包时只包含合成例子与可公开验证摘要。

部分采用允许沿用某些旧组件。`kit_version` 不能单独证明每个组件都已更新，也不能证明工具知道每条项目规则的含义。没有新任务协议的历史任务仍然保留；`context.legacy` 表示未验证该协议，不是失败，也不是已获得新版能力。

## 6. 在途任务的生效边界

每个受影响任务分别记录已采用的规则或上下文版本、此次升级影响、实际送达与采用情况。共享文件改了只证明记录已更新，不能证明执行器读过或停止了旧动作。

- 与变更无关的任务继续；兼容的新能力可从后续任务开始采用，不为历史任务补表。
- 可恢复会话按[任务上下文合同](../02_TECH/TASK_CONTEXT.md)定向送达，保留采用证据。
- 一次性调用不能中途送达时，保持待送达，返回后核对受影响成果，再验收。
- 已知旧动作违反现行用户约束时，使用实际可用的执行控制协调受影响动作，不能以“固定旧版”为理由继续认可。
- 现场未知时先核对指定会话、工作目录、产物和运行操作；不要重新派发，也不要宣称已经完成切换。

工具不控制外部模型或后台进程，Markdown 也不构成执行锁。必要检查点与纠偏记录属于授权任务的正常维护，不要求每轮总结，不依赖原生压缩通知，也不启动清理。

## 7. 对用户只交付实际结果

简短回执应说明实际采用、沿用与未覆盖范围；核对保留的关键业务约束；在途任务如何处理；检查和独立接手结果；日志位置与回退边界。确有不能从材料裁定的问题时，给出具体冲突，而不是把技术映射或填表工作转交用户。

用户主动发起升级，上游 push 不向目标传播变更。当前没有后台版本检测、自动升级、定时切换规则或自动清理。只有用户主动要求“依据文档治理整理哪些文档”时，才进入[文档生命周期](../00_PROJECT_CONTROL/DOCUMENT_LIFECYCLE.md)流程。
