# 已有项目的治理升级方案

方案版本：1。方向依据：2026-09-27 用户确认的成熟项目升级讨论。本文是实施依据；方案本身不证明升级工具、隔离试点或业务项目迁移已经完成。实施进展只在[当前状态](../00_PROJECT_CONTROL/PROJECT_CURRENT_STATUS.md)维护。

## 1. 要解决的问题与成功标准

用户通常把工具包链接交给正在开发项目的 AI，要求接入文档治理。项目继续开发后，治理规则、业务约束、历史决定和执行记录会发生本地变化；其中一部分项目从未使用标准安装器。

升级应让这些项目采用新的治理能力，同时保留已经形成的项目理解和开发现场。不能以“文件没有丢”代替成功：如果升级后把用户否决的导入恢复重新当成需求，或把已经实现的功能当成未开发，即使全部文件都在，也是失败。

本方案采用以下顺序：**识别现有职责和实际采用情况 → 调整后续事实维护方式 → 在隔离副本验证局部适配 → 提炼通用升级能力 → 在目标项目明确的任务边界生效。** 先用真实复杂度检验方案，再确定工具接口。

承诺的是可审查的变更范围、可追溯的依据、可核对的执行切换和局部回退能力。无损理解、零干扰、所有项目一次自动升级成功，均不作为已实现保证。

## 2. 已观察事实与现有能力

以下是方案形成时的观察，实施前必须重新核对，不能作为业务项目的永久当前状态。

| 观察 | 对方案的影响 |
|---|---|
| 实际成熟项目已有专题合同、事实索引、决策、验证和派工记录，但缺少新版根 manifest 与检查脚本 | 应走已有治理适配，不凭 `project-os/` 目录名猜测安装版本 |
| 同一入口并置“最新、尚未实施”和“已经完成”，靠顶部新段落解释下面是历史 | 需要分清有效现状和历史依据，不能仅根据标题、位置或时间选结论 |
| 事实索引仍称某功能未实施，但功能合同与代码已有实现 | 验证须涉及当前事实与下一步判断，不能只检查链接和文件存在 |
| 一次方向记录更新了九份文档，旧规则本身要求同步多个入口 | 优先修正继续产生重复状态的维护规则；不能只归咎于某次 AI 写得多 |
| 用户先探讨完整备份恢复，随后收缩为仅供查看的分类导出，形式仍未确定 | 必须保留后续修正、非目标和待定项；早期建议不能重新取得需求地位 |

v1.3.0 的现有能力是增量 `plan/apply`、本地 `check/snapshot`、用户主动请求下的只读 `inventory`，以及可选任务上下文合同。`apply` 保留已采用内容，不是升级命令；上游 push 不会更新目标项目。来源 revision 不是逐组件的实际采用证明，现有工具也没有自动语义合并、升级事务或自动回退。

## 3. 不可丢失的边界

- 保留目标代码、Git 身份、未提交工作、业务要求、历史决定、真实证据和进行中的任务。上游模板不授予改变产品需求或实际执行权限的权力。
- 继续使用 `rules/status/handoff/decisions` 四个全局来源。已有同等职责优先映射；不建立全局 `MEMORY.md` 或第二套当前状态。
- 专题业务合同继续留在原位置。目录式决策和已有派工体系可以通过索引导航，不要求改写所有历史为一种模板。
- 当前要求、当时的决定和历史验证分别保留身份。区分用户确认、候选建议、待验证假设、已实现和已验收；升级不晋升任何一种声明的效力。
- 必要的当前事实修正和规则适配，只发生在授权升级所需的明确范围。全库盘点、合并压缩、归档和删除仍须用户明确请求，升级不自动启动或询问是否清理，也不以全库清理为前置。
- 旧任务无需补造派工、检查点、送达或采用历史。新协议从能查证的现场开始；“未知”必须保留为未知。
- 业务项目的原文、私有代码、凭据、真实运行数据和会话标识不随工具包公开。公开验证使用合成或经核对可公开的材料。

方案编制时仅要求保存文档，用户随后已授权开始落实。实施继续遵守本文范围；方案本身不构成调用供应商、停止无关进程或发布业务内容的指令。

## 4. 升级对象按职责识别

| 对象 | 处理原则 |
|---|---|
| 工具包管理的检查脚本及通用资源 | 核对原采用版本、本地差异和新版变化；本地未定制的组件可按明确版本替换，有定制则合并 |
| 已融入项目的治理规则 | 识别每条仍有效的职责与来源，保留项目特有约束；同时检查文字差异和含义冲突 |
| 项目要求、专题合同、当前事实与待办 | 继续由项目维护；只修正本次适配相关且有依据的错误或重复事实归属，不以新版模板重建 |
| 历史决定、验收、快照和旧回执 | 原有证据保留；新结论通过替代关系或当前来源表达，不倒改历史为通过 |
| 活跃任务与执行现场 | 保留具体身份、工作目录、原上下文及操作定位；根据影响安排采用时点，不批量重置任务 |

拥有旧安装基线时，比较“原实际采用内容、本地当前内容、目标版本内容”。旧基线缺失时，不制造三方合并假象：从当前文件、来源记录、相关代码与证据重建可确认的职责，只对可判定部分形成补丁；无法判定的实质冲突单列。

本次采用后应留下下次升级需要的最小记录：源 revision、组件/规则职责、对应路径、实际采用内容或可重建的补丁与基线、摘要、本地定制及检查结果。仅有 hash 不足以重建内容。记录目标是避免下次从零调查，不要求给每份业务 Markdown 建版本账本。

记录格式及是否扩展 manifest，待试点验证后决定。不能只改 `kit_version` 就声称所有能力已采用；应能说明哪些已采用、哪些沿用、哪些未覆盖。

## 5. 先改变今后的事实维护方式

日常收到“把这个记录到文档治理”时，只落实用户本次确认的内容及必要来源，不把全部讨论、AI 建议或未明确的选项自动转成需求。

1. 找到本主题的权威文件，原位维护有效结论、来源、适用条件、明确非目标和待定项。
2. 确有重要选择或方向修正时保留决策依据；变更记录与验证记录只承担各自需要的职责，不为每次文字修改机械生成整套材料。
3. 当前状态、待办与交接按职责引用专题或任务；入口不各自保存同一份业务进度正文。
4. 状态改变时更新其唯一当前位置，历史依据继续可追溯。不能不断在多个文件顶部叠加“下方全部属于历史”作为长期维护办法。
5. 修改几个文件不是验收指标。每处写入必须有独立职责；仅为保持多份相同叙述而写入，属于需要消除的重复维护。

例如，分类导出的专题文件维护“用于查看、不做导入、形式待定”；决策记录保留为何收缩范围，待办指向专题，规则入口只说明去哪里读。以后改变导出方向时，无需寻找多个入口中的同义段落逐一修正。

调整后续维护方式不自动授权清理整个历史。适配必须接触的活动入口，可在保留唯一内容及来源的前提下，修正失效的“当前”表述或以明确引用替代重复陈述；无关历史保持原位。

## 6. 实施顺序与每步交付

| 步骤 | 工作与交付 | 可以进入下一步的依据 |
|---|---|---|
| A. 建立实际基线 | 识别标准安装、已有自定义治理或未接入；读取必要入口，记录 Git/未提交状态、相关文件、当前写入者及操作；给出职责与冲突表 | 能指出应保护的内容、未知来源和最小变更范围；不凭猜测赋版本 |
| B. 准备隔离样本 | 从获准的成熟项目材料制作必要副本；包含与场景有关的未提交事实，记录内容版本，排除生产数据和凭据 | 副本可独立读取；不连接真实执行器、数据库、供应商；测试不能影响原工作区 |
| C. 在副本适配 | 映射四项职责，先修正多处重复维护的规则，再形成局部入口/工具补丁；必要事实冲突查原依据；保留旧目录及历史记录 | 每个补丁可解释目的；业务边界和待定项未被改变；没有强制重建历史 |
| D. 验证接续行为 | 对照预先封存的答案，让没有原聊天历史的 AI 从正常入口接手；检查正确下一步、约束、状态与在途执行判断 | 第 8 节相关案例有实际证据，失败项修正后仅复测受影响范围 |
| E. 提炼通用升级能力 | 将试点中重复且可可靠判断的步骤实现为可审查的升级规划、应用与回退支持；保留语义冲突的显式出口 | 能覆盖有基线、缺基线、本地定制、并发变化、部分失败及回退；不把演示脚本冒充通用能力 |
| F. 目标项目采用 | 在用户授权升级后核对副本以来的新变化，重建受影响补丁，协调实际写入范围及任务切换，验证并登记真实采用结果 | 不覆盖期间新工作；实际项目入口能正确接续；回执说明采用范围及未测项 |

A–D 是首轮重点，不能跳过真实样本而先设计大型升级框架。标准版本迁移与自定义治理适配需要分别验证，试点成功不自动证明任意项目兼容。

Git worktree 只包含其提交基线，不自动携带原目录未提交的治理事实；副本准备必须核对这一差异。未提交工作本身不是要求用户先清空工作区或停止全部开发的理由。

## 7. 进行中的开发与回退

升级准备和独立检查可以并行进行。应用前重新核对受影响文件是否变化；有变化则重新比较该部分，不用旧副本覆盖新工作，也不自动 stash、reset 或强制切换业务分支。

对活跃执行，分别说明当前采用的规则/上下文、升级影响和实际生效时点：

- 与本次变更无关的任务继续执行，不要求全部停工。
- 对兼容的新能力，可以从后续任务采用，不追溯要求旧任务补表。
- 影响正在执行任务的约束，按[任务上下文合同](../02_TECH/TASK_CONTEXT.md)保存新版本、送达与采用证据。一次性调用无法中途接收时保持待送达，返回后核对受影响成果。
- 旧任务包含已知会违反现行用户约束的动作时，不能以“固定旧版本”为理由继续认可；使用实际可用的执行控制协调受影响动作。文件更新不等于已经停写，现场未知时不能宣布完成切换。

应用机制应有写前检查和逐项可恢复记录，明确部分写入失败后的状态；不把当前 `apply` 描述成已有跨文件事务。应用后版本登记只反映已完成的实际范围。

回退仅撤销本次治理升级引入的变更。如果文件随后又发生业务修改，先比较再形成逆向补丁；不得用旧整库快照覆盖新工作。数据格式或规则若出现不可逆迁移，应先在方案中暴露具体影响，不能默认为可回退。

这里的“可回退”针对治理适配，不为业务产品增加导入恢复、整库备份或云同步功能。

## 8. 验收场景

预期答案必须在盲接前确定，并绑定被测副本的版本；不交给接手者。真实项目在以后继续开发，预期事实随原依据重新核对，不能永久沿用本文形成时的状态。

| 场景 | 必须观察到的行为 |
|---|---|
| 先讨论恢复、后明确只做分类导出 | 找到最后有效决定；保留“供查看、不做导入、形式待定”，不把旧建议重新列为待开发功能 |
| 三条未来视频路线与已有脚本共存 | 区分方向确认、已实现脚本、未实施成片；不把未来能力当成已经交付 |
| 旧事实索引称文案未实施 | 查合同和实际代码/证据后纠正现状；不重复开发；也不由有代码推定质量验收通过 |
| 首页的旧计划与实现记录并置 | 定位当前适用范围，区分历史与有效合同；不单凭“最新”标题下结论 |
| 用户只要求记录一个新方向 | 更新必要来源和引用；不把所有建议晋升为需求，不重复广播状态，也不启动全库清理 |
| 活跃执行未收到升级依据 | 保留原会话与现场，明确待送达；不重派、不伪造采用、不按旧依据直接验收受影响结果 |
| 文件在规划后发生变化 | 发现变化并重建相关差异，不覆盖期间的新业务工作 |
| 历史任务无新协议、本地规则有定制 | 如实报告兼容与覆盖范围，保留定制；不补造历史或仅改版本号报完成 |
| 升级应用失败或需要撤销 | 能说明已经写入哪些内容；局部恢复本次改动，保留后来新增的工作 |

结构检查、文件保留检查、接手行为和真实执行切换分别留证。只改文档时做相称的链接、diff 与语义审阅；只有实现升级工具后才增加对应行为回归，不写仅重复方案正文的测试。

维护负担以实际观察记录：同一事实独立维护了几处、必要阅读量、额外人工纠偏、升级改动和等待范围。没有对照就不报告节省百分比；不以文件减少数或模板填满程度代替效果。

## 9. 用户入口、提问与交付

目标体验是用户给出项目与工具包链接，要求“升级当前项目的治理，保留已有积累并协调正在执行的任务”。AI 识别目标、完成可逆规划和已授权的普通合并，给出具体结果，无需用户填写迁移表或逐文件审批。

只有无法从现有材料裁定、且会改变实质意图、事实权威或授权范围的问题才提问。说明冲突来源、推荐和影响，保留原材料，只暂停依赖答案的动作；不把常规映射或技术实现选择上交用户。

升级由用户主动发起。首版不添加后台版本检测、跨项目自动推送、自动切换规则或定时任务。未来若增加更新发现，也必须区分“发现新版本、生成可审查差异、实际采用”三个动作；本方案不提前实现它们。

最终交付应能简短回答：实际采用了哪些能力，哪些沿用或未覆盖；哪些项目事实已核对保留；在途任务如何处理；完成了哪些检查；如何撤销本次改动；是否存在一个确需用户决定的问题。完整依据归相关证据，不重复到所有入口。

后续执行从步骤 A 开始。若要调整本方案，说明新证据、受影响范围与替代关系，不在后文悄悄恢复自动清理、全量重建、版本号冒充采用或无损保证。
