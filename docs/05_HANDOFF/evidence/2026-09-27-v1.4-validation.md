## 成熟项目的隔离适配

2026-09-27 从已有自定义治理中选择 49 份必要文档、历史任务和静态代码证据，包含相关未提交材料。没有复制 Git 目录、凭据、数据库或生成产物，没有运行业务服务或供应商调用。原项目没有可确认的工具包安装基线，未根据目录名推断旧版本。

适配六份现有治理入口，增加两份导航以复用目录式决策和阶段交接；专题业务合同、历史任务正文、验收证据和业务代码保持。修正已确证的事实失步，去掉要求每次向多个入口广播相同状态的维护规则。适配保留原有目录，未运行全库盘点或清理。

在派出独立接手者前封存预期答案，随后由没有原聊天历史的独立 AI 从正常 AGENTS 入口只读接手。封存预期摘要：`07b48a279dd4423748043388e2ca97da43e3d9e8902f5f82f9e3306418071cd4`；被测文件清单摘要：`733915fdd1f2213b3704e89befe05729604ac0b335b36c5ca8c71c3f3534bfe5`。摘要用于定位私有记录，不能单独证明内容真实或理解正确。

| 场景 | 实际观察 |
|---|---|
| 早期恢复提议被收缩为查看导出 | 保留不导入恢复、形式与范围待定，未擅自选定包格式 |
| 已有功能与未来路线并存 | 区分已有脚本与尚未实施的成片路线，未推定价格和排期已定 |
| 旧索引误称功能未实现 | 查专题、实际路由和验收，判断不应从头开发，未把实现视为全面质量通过 |
| 旧待开工计划与后续实现并置 | 找到当前实现证据，没有恢复历史派工 |
| 只记录一个新方向 | 选择相关权威与必要引用，不广播相同状态、不触发或询问清理 |
| 旧执行者未收到纠偏 | 区分记录、送达、采用及运行未知，不重复派工或按旧约束验收 |
| 业务约束和未验收范围 | 保留资料版本、费用、取消、失败稿及质量边界 |

另一次语义复核发现“把整段旧运行合同标历史”会连带弱化仍有效的约束。已恢复运行合同的效力，只有具体存在替代依据的条款才按新依据解释；混合日期的阶段标题也改为中性的范围说明。仅对这两处修正做了独立复核，没有重复整场试验。

随后在另一个隔离副本执行实际写入演练，给同一独立接手者一条模拟的新方向，要求仅记入治理。首轮只改专题和待办，但待办仍复制了具体限制，形成第二处维护位置，因此没有直接认定完全通过。补充“待办只保留状态、下一动作和专题引用”的明确规则后，仅返修该待办行；复查确认完整限制和待定项仍在专题中，待办改为链接。没有写业务代码、追加所有入口或触发清理。模拟业务决定没有带入真实目标。

这次观察证明该场景中的维护方式可纠正，不证明所有请求都会自动只修改两个文件，也不能用不同请求的文件数量计算节省比例。

试验还发现未修改的专题和待办保留一些旧状态。接手者正确按合同、代码及证据核对，没有把它们直接当作新任务。入口依然较长，本次没有完成全库压缩，不能报告阅读量减少或长期效率收益。静态副本也不是完整可运行产品，不能用本试验代替业务测试。

## 2026-09-28 发布收尾

再次只读审阅实现与公开材料，未发现正常升级路径的数据覆盖阻塞；发现非字符串 `mode` 和日志 `state` 会在写前抛出未捕获异常。已增加类型校验和两项 CLI 回归：错误输入返回结构化 JSON，目标文件与恢复证据保持不变。

修复后 Windows / Python 3.14 全套 **81 项**通过（146.178 秒），结构检查无错误或警告，99 个改动文档本地链接可定位，`git diff --check` 通过。最终脚本 SHA-256：`f1ddf386b3fba8be68ac6f19096c9aac1f7b02edeb440aac6fcd9f6b4de6ae66`；上面的 79 项及旧脚本摘要仍作为初次目标采用的历史证据。

语义复核进一步发现：整份协作合同标为历史仍可能弱化其中的稳定机制，旧运行强制句也可能被局部检索误用。升级指南和双语 README 明确区分阶段授权、稳定规则和具体替代条款；补充目标外日志的私有备份归属与连续升级先撤最近一次的边界。定点修正不构成历史清理，也不证明实际执行器已切换。

公开内容经过独立复核，只保留通用机制、合成例子与有限验证摘要。发布门槛为同一提交的四组 CI 成功；提交 SHA、运行链接及下载包摘要在 Release 保留，避免用未来发布结果反写成初轮本地验证。

## 未覆盖
